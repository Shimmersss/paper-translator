# 生产环境实测记录

[English](production-notes.md)

本项目从一个个人网站中拆分而来。2026 年下半年，网站上的版本一直在给一小群用户翻译真实论文，部署在一台 2 核 / 4 GB 的云服务器上，同机还跑着其他几个服务。本文记录实际译文效果、生产环境踩过的坑以及因此做的改动，供打算自行部署的人参考，尤其是小内存机器。

网站版本与本仓库接近，但并不完全相同，区别见[生产版与本仓库](#生产版与本仓库)。

## 实际译文效果

截图取自一次真实的生产翻译：*RT-2: Vision-Language-Action Models Transfer Web Knowledge to Robotic Control*（[arXiv:2307.15818](https://arxiv.org/abs/2307.15818)，© 2023 Google DeepMind）。该文于 2026 年 9 月用 BabelDOC 0.6.2 和网站默认的对话模型翻译，下载的是双语对照 PDF（左为原文，右为译文）。下列截图只截取局部用于展示效果，不构成论文译本；阅读请以 arXiv 原文为准。

### 标题页与摘要

![RT-2 第 1 页：左为英文原文，右为中文译文](images/rt2-page1-bilingual.png)

- 标题、作者列表、单位说明和摘要都在原位置译出，字体和行距接近原文。
- 作者姓名被音译成了中文。有些读者更希望保留原名，目前流程里没有强制任何一种做法。
- 右侧两行页眉连在了一起：日期被接到项目网址后面（“…github.io2023年8月1日”）。页眉页脚这类小文字块是版式里最容易出问题的部分。

### 插图

![RT-2 图 1：矢量图内的标签也被翻译](images/rt2-figure1-bilingual.png)

- 矢量图里的文字也会翻译：分栏标题、问答气泡、“Co-Fine-Tune”“De-Tokenize”“Deploy”都变成了中文。位图内的文字保持原样（那部分由单独的图片翻译功能处理）。
- 小框里的标签会显得拥挤。ΔT/ΔR 动作向量的排版乱了，部分照片说明与图像重叠。插图内容重要时，请对照原图核对。
- 图注完整通顺，其中的网址保持原样。

### 含表格的正文页

![RT-2 第 9 页：正文、图 5 与表 1](images/rt2-page9-bilingual.png)

- 正文、小节标题（“定性评估”“定量评估”）和行内引用译得很好，引用保留拉丁字母人名（“Fisher, 1936”）。
- 表 1 丢了一行：“LAVA (Lynch et al., 2022)” 消失了，它的分数 “77 ± 4” 落到了 RT-1 下面。BabelDOC 最常在表格短单元格里丢字或合并文字，译后表格中的数字请谨慎对待。
- 表注把引用 “Lynch and Sermanet, 2020” 音译成了中文，正文却没有。图表注释与正文之间不保证一致。

### 没有翻译的部分

这篇论文第 13–26 页是参考文献和附录，全部保留了英文。参考文献保持原文是有意为之。附录本应翻译，却没有翻译，原因有两个：

1. 这次翻译早于附录规则上线（规则于 2026 年 10 月加入）。
2. 即使是 10 月的规则，也识别不了 RT-2 的附录标题（“A. Contributions”“B. Datasets”……），当时只认 “Appendix …”、“Supplementary Material”“Acknowledgements” 等关键词标题，以及带论文短标题前缀的写法。v0.2.0 之后的 `main` 已能识别字母编号标题，见[第 5 条](#5-参考文献与附录)。

## 2 核 / 4 GB 上的速度与内存

以下数据在生产服务器上测得，使用单页分片。每页分别用三种并发各跑一次，交错进行，使缓存和网络条件可比。

| 同时请求数（qps） | 每页翻译阶段 | 每页总耗时 |
| --- | --- | --- |
| 2 | 26.3 秒 | 约 51 秒 |
| 4（网站默认） | 15.4 秒 | 约 40 秒 |
| 6 | 13.1 秒 | 约 38.5 秒 |

- 每页约有 20 秒花在把文字发给模型之前：启动 Python 并导入 BabelDOC 约 7.7 秒，版面与公式解析约 12 秒，后者每页都免不了。
- qps 超过 4 后提升很小，因为每页的固定开销占了大头。
- BabelDOC 进程峰值 PSS（按比例分摊的实际内存）为 2.1–2.5 GB，与 qps 无关。可用内存的最低点（380–770 MiB）出现在排版阶段，而不是翻译阶段。
- 测试期间模型服务商没有返回过限流（429）。

## 踩过的坑与对应改动

每条写明现象、原因以及修复所在。“本仓库已有”表示 `main` 分支的代码包含该修复，其中标注“v0.2.0 之后”的尚未进入正式发布版本；“仅生产版”表示网站已有、本仓库没有。

### 1. 内存：4 GB 机器上最难的部分

| 现象 | 原因 | 改动 |
| --- | --- | --- |
| 整个后端卡死：负载约 26，健康检查超时，SSH 断连。 | systemd 的 `MemoryHigh`（2200 MB）低于应用自己的内存保护线，应用还没来得及停掉 BabelDOC，内核已开始限制整个服务。 | systemd 限制要高于应用保护线。网站现在用 `MemoryHigh=2700M`、`MemoryMax=2800M`、`MemorySwapMax=1200M`。 |
| 正常任务在 2404 MiB 和 2522 MiB 被杀。 | 2400 MiB 的保护线低于 BabelDOC 的正常峰值（处理文档时约 2.6–2.8 GB）。 | 提高保护线。降低 qps 并不能降低这个峰值。 |
| 进程并不大，任务却失败。 | 保护线读的是 `memory.current`，里面包括前面分片留下的文件缓存。 | 改为统计工作集：`memory.current − inactive_file`。**本仓库已有。** |
| 可用内存跌到 53 MiB，触发硬保护。 | `vm.swappiness=0`，Swap 根本不会被用上。 | `vm.swappiness=20`，并给服务单独设 Swap 上限。 |
| 三页一个分片仍然超峰值；把分片从 5 页缩到 3 页也没用。 | 峰值来自每页的版面处理，分片大小只会改变它出现的位置。 | 4 GB 机器固定单页分片；内存紧张时并发按 4 → 2 → 逐页 降级。**本仓库已有**（默认每片 1 页）。 |
| 服务器运行一个月后，任务因“Swap 已满”被拒。 | 整机 Swap 里有其他服务的冷页。 | 只统计本服务自己的 Swap（`memory.swap.current`），系统剩余 Swap 只保留 256 MiB 底线。**本仓库已有。** |

在小机器上部署时：应用保护线要低于 systemd 限制，保留一定 Swap，并用真实的多页 PDF 测试。很短的测试文档达不到峰值。

### 2. 任务启动时下载分词表

- **现象：** 第一个分片就报 TLS EOF，一页都没翻译。
- **原因：** BabelDOC 依赖的 tiktoken 首次使用时会从 Azure 下载 `o200k_base`，而服务器到那里的网络不稳定。导入 BabelDOC 时还会覆盖事先设好的缓存目录。
- **改动：** 分词表随应用发布，使用前校验 SHA-256；runner 在导入 BabelDOC 后恢复缓存目录。**本仓库已有**（`backend/scripts/tiktoken-cache/`）。升级 BabelDOC 或 tiktoken 时，记得核对源 URL、缓存键和哈希是否仍然一致。

### 3. Java 自动升级导致翻译失败，健康检查却仍返回 200

- **现象：** 任务停在 0%，日志报 “Incorrect Java version” 和 `jspawnhelper` 版本不符，而 `/api/health` 一直返回 200。
- **原因：** unattended-upgrades 在 JVM 运行期间替换了 JDK。旧 JVM 无法再启动子进程，而每次翻译都要启动一个 Python 子进程。
- **改动（运维）：** 把 OpenJDK 排除出自动升级。在没有任务运行时手动升级 Java，重启服务，然后实际翻译一次。只看健康检查不能证明 worker 能启动 BabelDOC。

### 4. 扫描版 PDF

| 现象 | 改动 |
| --- | --- |
| 一篇 12 页的扫描论文，BabelDOC 报 “no paragraphs”。 | 没有文字层的页面先做 Tesseract OCR：页面转为背景图（最高 300 DPI），上面叠一层隐藏文字。**本仓库已有。** |
| 译文字号只有原文的约 63%。 | 隐藏文字的字号按实测字形高度（÷ 0.86）计算，并按每页的实际笔画校准。 |
| 一个段落被拆成 92 段。 | 按阅读顺序写入隐藏文字，同样的两栏页面现在得到 12 个完整段落。 |
| 引用编号上出现黑块，标志和封面被弄乱。 | 小于半页的嵌入图片（标志、封面、插图）不做 OCR。 |

### 5. 参考文献与附录

- **现象：** 参考文献后面的附录保持英文，任务却显示“已完成”。
- **原因：** 一旦进入参考文献区，后面的内容都按原文保留，直到遇到结束该区的标题；最初只有单独一行 “Appendix” 才算这样的标题。
- **改动：**
  - 带编号或标题的附录，以及 Supplementary / Supporting / Methods / Acknowledgements 等标题，现在都会结束参考文献区。**本仓库已有。**
  - 带论文短标题前缀的写法（如 “GraspGen-X: Supplementary Material”）也能识别。**本仓库已有。**
  - 修复前缓存的分片需要作废。提高缓存版本号并不管用，因为兼容性检查会忽略 `version=` 行，所以改为新增一条策略行（`references=titled-appendix-v1`）。
  - LaTeX 风格的字母编号标题也会结束参考文献区：“A. Contributions”“A.1 Training Details”，或单独一行 “A” 且下一行像标题（“A” / “Discussion: Selection Mechanism”）。只认 “A”，因为它是第一个附录。标题不能含逗号、分号、年份或 “et al”，也不能以句号结尾，这样 “A. Radford, J. W. Kim, …” 这类作者行仍留在参考文献里。单独的 “A” 必须配标题行，因为有些 PDF 会把参考文献逐词提取成一行一个词（“Mish: / A / self”）。在个人文献库的 25 篇论文上测试，该规则只在真实附录处结束参考文献区（RT-2、Mamba、OpenVLA、LiLa-WAM）。缓存分片新增策略行 `references=lettered-appendix-v1`。**本仓库已有（v0.2.0 之后）。** 网站代码已改，尚未部署。

### 6. 重试不完整响应并提示未译段落

| 现象 | 改动 |
| --- | --- |
| BabelDOC 吞掉了服务商报错，交付的“译文”其实是原文，用户还被扣了费。 | 记录最终逐段请求的失败，交付时提示保留了原文的段落。完整性检查仅作提示，不阻止交付。**本仓库已有。** |
| 部分段落返回空结果或被截断。 | 先依次加大输出额度重试（4096 → 8192 → 16384 token），仍失败才放弃。**本仓库已有。** |
| 服务商下线了某个模型，每个请求都返回 HTTP 400。 | 设置页提供“测试连接”按钮，`paper-translator doctor` 也会检查模型，不必等一次真实翻译才发现。**本仓库已有。** |
| API Key 被吊销或过期，每页都返回 401。 | 重试仍失败时保留原文并提示。可用“测试连接”检查 Key。 |

### 7. 推理模型把输出额度全花在了思考上

- **现象：** 一个分片卡了约 10 分钟后失败，模型返回空答案，`finish_reason=length`。
- **原因：** 该服务商的 v2.6 模型默认开启推理。一个 923 token 的段落把 4096 个输出 token 全用在推理上，加大额度后也一样。
- **改动：** 对该服务商的模型关闭推理（`thinking: {"type": "disabled"}`），并把这个参数计入翻译缓存键。**本仓库已有（v0.2.0 之后，对 `mimo-` 开头的模型生效）。** 如果你的服务商默认开启推理，请关掉它，或换用非推理模型。

### 8. 一次批量请求被拒，整篇失败

- **现象：** 每个段落最终都译出来了，文档却仍然失败。
- **原因：** BabelDOC 以 JSON 批量发送段落，批量结果被拒时会回退为逐段请求。可完整性检查在批量被拒时就把文档标记为不完整，逐段回退成功也救不回来。
- **改动：** 只有最终的逐段请求失败才计入未译段落，批量失败后补译成功不计入；统计报告中附上失败原因。**本仓库已有（v0.2.0 之后）。**

### 9. 三十页的论文不该因为几段原文而失败

- **现象：** 一篇长论文在多次重试后仍有几个段落是英文，整篇因此失败。
- **改动：** 完整性检查仅作提示，不设未译段落数量或比例门槛。整页未译、失败段落无法定位页码时也允许交付已生成的 PDF，任务完成后提示已知受影响页码，各分片统计写入 `paragraphs.json`。进程报错、超时或缺少 PDF 文件仍正常判为失败。**本仓库已有（v0.2.0 之后）。**

### 10. 被杀任务留下的临时文件

- **现象：** 服务器磁盘只剩 448 MB。
- **原因：** 被内存保护杀掉的任务在 `/tmp` 留下了 59 个 BabelDOC 工作目录，每个都有一份上传 PDF 的副本。
- **状态：** 已手动清理。**仍未解决：** 服务还不会自动清理这些目录。

### 11. CI 与打包

- macOS 构建机升级到了 Python 3.15，而它没有 onnxruntime 安装包；BabelDOC 命令现在固定 `--python 3.12`。
- Windows 检出时改写了分词表的换行符，导致哈希不符；`.gitattributes` 已把它标为二进制文件。
- 发布包的链接检查在 Windows 路径上失败；现在所有平台都按 POSIX 形式检查包内路径。

### 12. 图片翻译的文字框

视觉模型给出的文字框只是大概位置，遮盖时要么漏掉部分原文，要么盖住旁边的图案。现在每个框在遮盖前都会对齐到实际笔画（`TextBoxRefiner`）。**仅本仓库**，网站仍在用旧的图片翻译流程。

## 已知问题

- **少见的附录标题**（如 “Supplement S1”，或只有标题没有编号）仍可能让附录保持英文、任务却显示成功：这些页面没有可翻译段落，“不允许整页未译”的检查不会触发。
- **表格：** 短单元格可能丢失或合并（见上文 RT-2 表 1）。
- **插图里的小标签** 可能重叠或排版错乱。
- **人名：** 作者姓名可能有的地方被音译，有的地方保留原文。
- **OCR** 有时认错符号，例如把 ε0 认成 “¢9”。引用编号可能与译文重叠，灰色页眉里可能出现白块。
